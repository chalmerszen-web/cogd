# 0.8.1 播放与响应时延修复（2026-11-05）

实物：ESP32-P4-WIFI6-Touch-LCD-3.5，16 MiB Flash / 32 MiB PSRAM，实际 CPU 200 MHz。P4 直接连接千问 `qwen-audio-3.1-realtime-flash`，同一音色 `longanqian_v3.1`，默认仍为 `smart_turn_v2`。

## 结论与边界

连续播放卡顿的主要原因已定位并修复；**500 ms 端到端自然回答尚未达到**。当前短问答在外置房间麦克风上的估计出声时间为 1.965 / 2.075 秒。测试使用固定耳机回放和实物收音，不能代表真人、远场、噪声总体成功率或 P95。

降低静音判停到 400 ms 的实验为 1.388 / 1.633 秒；450 ms 句中停顿被拆成多次回答，其中一次返回生成失败。因此未作为默认配置。官方说明该参数仅对 `server_vad` 有效，且越短越容易把停顿当成结束；语义模式不能通过设置这个参数加速。[千问官方参数说明](https://help.aliyun.com/zh/model-studio/fun-audiochat-client-events)

一般联网问答的时延还包括判停、网络和云端生成，P4 增加内存并不能给这些环节提供 500 ms 上限。限定意图的本地操作、缓存语音是后续满足硬时延指标的可行方向；任意开放问答、搜索和生成不能用这个指标作当前交付承诺。

## 已修复的原因

旧版网络任务先将 PCM 放入 45 秒大队列，再每轮最多转交 80 ms 音频到 8 KiB 小队列。网络接收单轮实测最长 487 ms；20 秒样本中，即使大队列还有约 14 秒音频，小队列仍断粮 162 次。独立本地正弦测试中，3 秒实测 DAC 参考没有 5 ms 静音块，回声处理正常，因而不能把问题归咎于喇叭或简单加大音量。

修改后由原有音频任务直接读取大队列，网络任务只解码和原子发布采样。取消时先等播放任务归还缓冲再清理，容量和索引同时计入已经发布但未播放的数据。移除了 8 KiB 中转缓冲，没有新增任务或服务。首播预缓冲为 80 ms，功放静音预热与云端生成重叠；收到新 PCM 后立即交给音频任务，不继续等待下一个网络块。

同时抑制扬声器残留回声触发云端新话轮：设备持续采音和本地插话检测，播报期间向云端送等长静音；本地确认有人插话后停止旧回复，从现有采音环补送最多 1 秒的起始人声，再继续实音上传。空闲噪声候选不再无止境地刷新会话活动时间。

## 有限实测

| 项目 | 结果 |
|---|---|
| 自然问答、连续接话、30 秒告别 | PASS；两次短回答，独立房间麦克风转写为“蓝莓” |
| 100% 音量整段故事 | 64.695 秒 PCM，板端计时 65.160 秒；0 次播放队列断粮、0 次错误取消、0 次重连 |
| 80% 音量插话、上下文回忆 | PASS；实际音源起声到本地停播确认 560 ms；独立转写“松果七号” |
| 100% 音量插话 | 内容正确，但停声确认 1,822 ms，未通过 1,300 ms 测试门槛；仍需优化 |
| 80% 音量、55% 测试源幅度的弱插话 | 内容正确，但停声确认 1,513 ms，未通过同一时限门槛；不能沿用上版 686 ms 结论 |
| 自然模式下的 450 ms 句中停顿 | PASS；只回复最终内容“白桃” |
| 音量、绘图与中文内容的工具调用 | PASS；真实回执后回答 |
| P4 原始 High/AAC 视频准备、播放、暂停、续播 | PASS；15.17 fps，0 音频断粮；串口触发同一触屏处理，未计为真人点击验收 |
| C3 共享音频代码编译 | PASS；未刷 C3 |

**仍有短暂停顿边界：** 故事中出现 1 次本地可疑回声确认，约 320 ms 暂停后恢复，未丢弃待播样本；它与旧版连续断粮是两个原因。当前不能声称所有音量、环境下完全无停顿，也不能把大音量和弱插话的慢打断列为通过。弱插话首轮没有进入官方唤醒后的实时会话，因此该轮没有测到插话；独立重试后的 1,513 ms 记录位于 `barge-weak-02`，未把首轮抹去或记作成功。

旧版留存的 73.820 秒 PCM 需要 85.948 秒板端播放；新旧故事由模型分别生成，不能当作同一音频逐样本 A/B，只用于与采样时长、断粮计数交叉核对。

普通问答的软件首音排队时间为 1.873 / 1.990 秒；实际麦克风估计另有约 86–92 ms 的硬件输出延迟。语义判停之前约 1.55–1.65 秒，不能把判停后约 0.4 秒的表现称为完整的 500 ms 响应。声学估计采用已知测试源相关对齐和 10 ms 语音频带能量阈值，存在噪声与首辅音检测误差。

证据：`evidence/playback-20261105/`。`diagnostic-run` 保存断粮复现；`final-01` 保存每项 PASS/FAIL；`barge-80` 保存同一固件的标准音量复核；`media-check-02` 保存视频回归。首次媒体脚本把预期的短暂 busy 当成失败，第二次使用有界状态重试重测；失败记录保留。所有主测试对应候选 SHA-256 `b0438518ad6a3359df64b84673a328a9f5f51f08db0dfc080a6fccea55c8f133`。

## 代码与架构

主要实现位于 `../platform/espidf/p4_conversation.c`、`../boards/esp_hi/audio_board.c/.h`。原音频任务负责麦克风消费和喇叭供音，原网络任务负责千问协议与上下文；后台工具任务沿用。本轮不替换 WakeNet10、音色、摄像头、LCD 方向、Wi-Fi 配网或模型回执接口。详见 [架构说明](ARCHITECTURE.md)。

诊断命令 `agent voice endpoint 0` 恢复默认语义判停；`200..800` 是临时声学判停实验，要求语音关闭且空闲，不写入 NVS。最终保留语义模式。
