## 代码与主机验证

`plugins/speech/candidate.c`在原子序列校验里增加一个内部连接词例外，既不能
独占话题，也不能代替话题两侧实词。生成提示同步说明这项许可。用193的五条
真实候选文本回归：可接受1/5→3/5，新增的两条都是“灯的颜色”；虚构白色、
过长主题仍拒绝。这只是固定五条文本的校验覆盖变化，不是唤醒/响应成功率。

测试覆盖前后缀连接词、重复连接词、倒序、新增名字/颜色/否定、语言不匹配、
改口及捕获未确认。完整69项ASan/UBSan通过，41.42秒。普通1501568B、
诊断1503040B、无音频1014096B。比193普通及诊断分别增加176B；无音频
二进制不变。普通/无音频不含诊断入口，399份代码与冻结194逐字节核对。

## 一组相同的五作业设备对比

使用UX155同一诊断脚本和五作业顺序，仅修改目标版本和独立输出目录。
固定输入、人工候选屏障、没有实时ASR并发；不能当作语音速度或完整负载通过。

| 作业 | 结果 | 实际覆盖 |
|---|---|---|
| pass | protocol | 模型说“灯光颜色”，新增“光”，按现有规则拒绝 |
| revision | done | 已备好候选，改口后不播放旧候选，正式回答完成 |
| cancel | cancelled | 延迟交接已进入；USB取消至终止约406ms，原捕获块接管成功 |
| failure | protocol | 完整正式请求已发出，注入失败后12ms内完成交接，原块接管成功 |
| pass | cancelled | 完整请求已发出，候选继续收了音频，之后无新PCM或结束消息，原期限取消 |

三个`candidate_request_overlap`是进入延迟路径；其中取消轮没有完整sent事件。
因此**完整请求体与候选并行是两次，不是三次**。三次`workspace_adopt`均明确
记录capture_arena，证明这三个退出路径没有交接时重分配状态区。
没有GPIO副作用、复位、WDT、panic或DMA丢失。未证明正常成功交接，更不能
用故障清理通过替代正常业务成功。

最后一轮的关键时钟：最终确认51872ms，候选排空51931ms，HTTP预热结束
52587ms，完整请求sent53219ms，开始join53220ms。候选最后PCM回调53577ms，
该回调同毫秒结束；之后仍轮询，到61892ms原截止时间取消，61896ms完成原块
接管。485次轮询，终止时message_open=false、response_done=false。
这将问题缩到候选后续接收/终止，不能再归因为“状态区连续内存分配失败”。

SDK最低堆46984B，网络栈最低1688B；SDK水位已在普通revision路径下降。
无实时ASR的本组不能证明完整并发资源通过，不能拿它与声学组直接比较收益。
音量80，原始外录在`device-194/speaker.wav`；人工等待造成的音频停顿不用于
主观听感或有效回答时延成绩。

## 排除项和下一步

现场源码检查发现IDF的TLS poll已检查解密缓存，WS poll也检查升级响应缓存；
不能直接断言“没有读缓存”。引擎在候选join之后才调用正式TTS预热，这次日志
中也没有在最后一轮提前打开TTS的事件，尚无证据指向该动作抢占候选连接。
记录的最后PCM回调很快，之后是轮询等待，也不能说播放写回调阻塞了八秒。

下一步用同一固定输入比较“只预热后join”和“发送请求体后join”，同时增加
有边界的接收字节/就绪计数，区分并行HTTP流量与候选接收本身。保持原超时，
不重放已发出的请求，不增加缓存/放宽未知状态。三轮完整语音回归仍为推广前
必要步骤。上述接收根因未确认，本轮没有凭推测修改TLS或扩大网络排空循环。
