# 候选接收与请求并行：UX157

2026-09-29。保留195诊断源码，默认关闭。设备已恢复0.11.72-summary，
本轮没有推广固件，没有完成一秒响应或完整语音目标。

## 有限实验

UX156已有请求发送后候选不结束的证据，但只记录PCM与解析器时钟。
本轮增加仅在`AGENT_HANDOFF_PROBE`构建存在的接收计数：SDK读、原始TLS读、
poll就绪/空/错误、交给WS上层的字节数与最后进展时间。计数随连接打开重置、
关闭后保留，主任务只在候选任务join后读取；没有改变读算法或超时。

新增warm模式：同样在候选已校验、首次排空后暂停，但HTTP连接预热结束就
恢复候选接收；pass模式在完整正式请求发出后恢复。原10秒期限不延长。
输入仍为“现在灯是什么颜色”，最终输入仍为“现在灯是什么颜色？请简单回答。”。
仅执行warm/pass/pass/warm/warm/pass六作业，无同版本自动重试。

首轮主机测试发现warm路径可能在预热前已完成任务，无法稳定形成所需对照。
修正诊断屏障，warm也保持到真实预热结束；重新通过69项ASan/UBSan，40.52秒。
首次失败日志保留。计数测试包括SDK转TLS、分片、空读/读失败、独立ASR连接、
关闭后保留、下次打开重置和饱和计数；原生产构建无这些资源。

失败3/6都成功接管原捕获块，没有再次分配状态区失败或工作区所有权悬挂。

0读失败；最后WS数据至结束8222ms，解析器没有打开的半条JSON。

第6次发送53783B；最后TLS/WS数据67303ms，最后就绪67357ms，75824ms截止。

这里的TLS计数是TLS解密读取返回的字节数（含WS帧头），不是无线抓包。
SDK部分计数是其WS读取返回的载荷；两个数字不能当同一层直接比较吞吐率。
记录支持“接收进展停止而仍在poll”，不支持“云端确定未发送”“物理网络断流”
或“某个TLS缓存处理错误”这些更强结论。当前证据也不能将因果唯一归到未读取
HTTP响应，分配、发送、等待交接等仍是两组间的不同因素。

SDK最低堆45256B，网络栈最低1684B，均为无实时ASR的诊断组；没有完整资源
门槛通过。观察到0DMA丢失/复位/WDT/panic/灯光副作用。音量80，原始实录
62.65秒、44.1kHz单声道，不做主观评分或声学延迟合格声明。

## 决策与下一步

不推广请求体并行，不重复同组六作业。保留只读诊断和warm控制路径。
下一项应只改变一个有机制依据的条件：验证正式HTTP响应暂不读取是否参与
停顿，可在诊断构建中先接收HTTP头，再join候选，保留所有响应字节及原期限；
若仍失败，再区分单纯请求缓冲分配与真实发送。该修改尚未实施，不能称为修复。
无句末标点造成缓存满也已单独记下，不能与网络等待混合后声称同一根因。
完整输入、改口、连续三轮声学验证和有效回答一秒目标仍未通过。
