## 机制与改动

UX164每次看到WS乱序pbuf和HTTP接收邮箱对象数下界为8，状态持续数秒不动。
固定SDK的wlanif_input在不拷贝模式让上层pbuf持有Wi-Fi L2缓冲；未消费HTTP
与WS乱序队列共同占用接收对象的证据支持这一解释。203开启SDK已有拷贝路径：
数据放入堆pbuf后即释放原L2缓冲，避免两条TCP流等待各自上层消费者时留住
Wi-Fi接收资源。没有增加RX8、OOSEQ4、TCP窗口5760、任务栈或应用缓存。

这是增加一次包拷贝及瞬时堆占用的取舍，不是无成本优化。三次小样本支持
该机制修复了本次故障，不足以证明所有网络条件都不丢包。未抓包定位全部
丢包位置，不把邮箱消息数当作精确驱动分配计数。

407份C/H/CMake仅runtime版本202→203，SDK仅该选项及其旧名兼容别名变化。
初次审计遗漏CONFIG_L2_TO_L3_COPY别名，核对SDK的sdkconfig.rename后修正
审计；没有额外参数修改。主机70/70证据沿用UX164，未虚列为本阶段重跑。
普通/诊断/无音频构建：1501856/1506448/1013968B。
