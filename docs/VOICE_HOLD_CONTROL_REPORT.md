# 暂停接收与请求缓冲对照：UX159

2026-09-29。197为默认关闭的诊断源码，设备恢复0.11.72-summary。完整语音
目标和一秒有效回复仍未通过。前一目标轮归类为进展：接收计数与HTTP读头
负结果明确改变了本轮的对照条件，没有把未完成目标缩小成诊断通过。

## 设计

沿用同一候选提示、固定输入及生产候选校验。delay/reserve都先完成真实HTTP
预热和延迟交接准入，再保持候选屏障650ms，随后join，最后才发送正式请求。
reserve仅增加真实`esp_agent_engine_memory_prepare`分配，其缓冲保留到正常
引擎使用；delay在join前不分配。原候选期限、取消和内存所有权不变。
650ms近似UX157两轮预热结束至sent的624/625ms，不是逐轮精确配对。

一次六作业：delay/reserve/reserve/delay/delay/reserve，无重试。没有实时ASR，
人工屏障只用于机制取证，不作为声学速度成绩。69项ASan/UBSan通过41.98秒，
包含650ms屏障保持及原取消/超时测试；普通、无音频、诊断构建均通过。

第1/4轮是两次有效的额外650ms等待后完整接收，分别恢复后1143/1328ms结束，
都收到response.done。单纯这一长度的额外暂停并不必然导致取消。
reserve三轮中，两轮没准入，一轮音频已收齐，因此**没有任何“已分配且仍需
接收”的有效对照**，不能宣称排除请求缓冲分配。

第3轮记录的空闲堆109712→84108B只是该时刻总变化，包含并行网络活动，
不能当作单次calloc的精确占用；请求缓冲逻辑容量仍为24577B。
四次延迟交接后的原捕获块接管均为capture_arena。所有正式请求都在候选join
之后发送，完整请求体重叠为0；日志名称candidate_request_overlap在这里仅表示
进入延迟API，不能把这四条日志误报成四次请求发送并行。

第6轮提供反例：没有请求缓冲提前分配、没有正式请求发送，候选仍未在原期限
内结束。预热97596→98600ms超时；最后WS数据107467ms、候选107553ms结束。
509次轮询、TLS poll空429次、无读错误；最后PCM107468→107471ms。
结束前仍有数据进展，现有计数不记录每个间隔，**不能称为与157完全相同的连续
8秒无数据**，也不能断言两类取消同根因。它至少说明不能将所有候选到期取消
都归因为发送正式请求。

组内SDK最低堆44068B、网络栈2396B，缺真实ASR负载，非资源验收通过。
未观察到复位/WDT/panic/DMA丢失/灯光副作用。原始外录82.75秒、44.1kHz
单声道、音量80，无主观听感或一秒回答合格声明。

## 后续取向

不因5次done推广固件，不补测直到得到所需分配样本。当前人工屏障会让连接
暂停接收，已影响测试条件；下一步应先用同样固定输入、保留诊断时钟但不钉住
生产者的入口验证正常候选任务是否完成，再回到至少三轮真实连续语音。
正常条件若不复现，就不能继续把被迫制造的并行失败当作正常路径的唯一卡点。
若复现，再用每次接收的最长间隔与公开socket指标定位，原超时仍不加长。
ASR完整输入、双语唤醒、VAD收尾、有效回答和上下文资源目标均保持。
