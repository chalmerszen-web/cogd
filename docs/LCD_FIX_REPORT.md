# 0.6.2-repair 修复记录

2026-09-16，COM5，ESP-HI / ESP32-C3 rev0.4。针对用户截图中的 `config`、`limit` 和实物屏幕不显示，修正对话和存储错误，并更换 LCD 传输实现。**实物亮屏仍未验证，不能称黑屏已修好。** 0.6.1 的 SPI 帧计数和模型声称成功均不作为实物通过证据。

## 查明的问题与修改

1. 开机 HTTPS 在时间未校准时直接返回 `config`。改为显示 `@wait clock`、最多等待 15 秒、检查断网及取消，超时仍明确报错，不跳过 TLS 验证。最终开机实测时间已经有效，非流式请求通过；该次未触发等待分支，未冒充校时超时/取消实机覆盖。
2. 用截图原句复现音乐 `limit`：收到的 JSON 仅 1,578 字节，11 乐句、104 音符；六个乐句超过 32 ticks，还有不存在的乐句引用。不是堆耗尽或 4 KiB 参数缓冲不够。增加整批预校验、原调用 ID 配对错误结果和最多两次纠正，未知工具/重复 ID/截断/已有执行不自动重放。首次泛化错误反馈仍失败，记录保留；最终用六乐句的明确时值模板引导创作，实际生成有效音乐。
3. 模型会把重启前“已经开启时钟”的历史当成现状。每轮 system 追加当前 LCD 状态和运行时间，明确帧数是传输信息，要求执行/查询工具后再报告。旧记录也有真实 `display_set` 成功，因此历史误判不是用户黑屏的唯一解释。
4. LCD 改用 ESP-IDF panel IO 管理 DC 和半双工 SPI。初次异步像素队列候选在大历史请求期间出现 3.126 秒 tick 墙钟停顿，已去掉队列；最终采用同步 64 字节小块、320 字节行缓冲，沿用参考 BSP 的寄存器、偏移和接线。复位等待从命令实际完成时计起。没有凭空写未知背光/复位引脚，没有读出控制器 ID。
5. 音乐已播放却在结尾报 `busy`：活动日志只剩约 24 KiB，旧逻辑为任何小记录都预留最大 24 KiB，触发不必要的压缩；播放期间擦除被资源仲裁拒绝。现按实际事件大小判断空间，仍保留全部历史、尾损坏恢复和真正满时的 `full`。

## 证据和使用

私有证据目录 `artifacts/lcd-fix-v1/`：原固件复现、各次失败候选、主机/构建日志、`boot-clock.json`、`music-final.json`、`final-song.json`、`music-complete.json`、`device-test-final.json`、前后完整 Flash、读回核验、NVS 校验及 release 清单。原音频未替换，仍为用户已有的 2.36 秒片段。0.6.1 与 0.6.0 回滚产物保持独立。

双击项目根目录 `打开设备对话.cmd`。普通文字回车即可；要绕过模型检查显示，直接输入：

```text
agent display set {"mode":"clock","foreground":0,"background":65535,"utc_offset_minutes":480}
```

该命令只启动设备本地时钟，不依赖模型猜测时间。重启默认关闭显示；`agent cancel` 也会关闭。最终留在白底黑字时钟模式。真实画面必须单独观察，软件成功未改写原 M0 外部同步/真实断电未通过项。
