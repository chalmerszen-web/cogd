2026-09-27，UX-36/37。**已接入设备并完成有界实测，但未通过速度、语义和内存验收。**
设备已恢复冻结的 0.11.72-summary，fast/capture 监听、reuse 开、prefetch 关。

## 改变方向的证据

上一轮[分段诊断](VOICE_PREFETCH_STATE_REPORT.md)发现，200ms 云端分段会把同一
改口句切成六段并漏词，800ms 也未完整。继续缩短静音阈值不能解决完整收听。

已有 `partial-manual-02/events.jsonl` 表明，手动提交模式在用户还没说完时就会
返回临时转写。本轮尝试保留同一条完整输入：上传不中断，将临时转写放入更新
的提示词，只请求一个可丢弃草稿；结束后一次性提交原音频，再读取完整转写。
没有新增第二条 TLS 连接，也没有切换模型。

官方说明支持[更新提示、手动提交及请求响应](https://help.aliyun.com/zh/model-studio/client-events)，
并定义了[临时转写与最终转写](https://help.aliyun.com/zh/model-studio/server-events)。
这些文档没有承诺上述并行组合和消息编号行为，因此先做有界协议实验。

## 两次主机协议实验

两次都使用上一轮设备保存的改口录音，16kHz、104576 样本、6.536 秒，追加两秒
静音。512 样本分块，实时上传，同一 `qwen3.5-omni-flash-realtime` / Tina。
每次最多一个草稿、一个正式回答，25 秒会话上限，无重连或重试。

| 检查 | 首次严格编号检查 | 后续编号观察实验 |
|---|---|---|
| 请求次数 | 1 | 1 |
| 提前收到草稿 PCM | 是，比文件结束早 1.536 秒 | 是，比文件结束早 1.489 秒 |
| 完整源音频全部上传 | 否，编号变化时停止 | 是，含统一静音尾部 136576 样本 |
| 最终完整转写 | 未收到 | 包含蓝色、否定及最后的绿色要求 |
| 显式音频提交 | 0 | 1 |
| 最终转写编号 = 提交确认编号 | 未验证 | 是 |
| 草稿可直接播放 | 否 | 否，已被后续改口推翻 |
| 播放 / 工具执行 | 0 / 0 | 0 / 0 |

第一次不是服务端拒绝请求：已生成草稿，但后续临时转写换了消息编号，客户端
按原断言停止。记录保留。第二次是明确新增的观察实验，记录有限数量的临时
编号变化，并核对最终提交与转写编号；没有改动设备现有的身份校验。

第二次草稿针对“请把灯调成蓝色。不对，不要”，回答“好的，那换成什么颜色呢？”；
后续完整转写是“请把灯调成蓝色。不对，不要蓝色，改成绿色。”。因此必须舍弃
草稿。原型成功保留整句且没有重传整段，但没有得到可接受的提前回答。

正式回答又说“好的，已为您调成绿色。”，而本实验没有工具和实际动作，属于
提前宣称成功，仍不允许播放。`complete:true` 仅表示该会话协议走完，不表示
内容、动作、听感或一秒指标通过。两次实验均 `accepted=false`。

时间以文件样本结束为参照，包含原录音里的停顿及尾部；它不是实际用户词尾。
没有用首 PCM、咻音或占位话语替代有用回答的扬声器起声时间。

## 已完成的 C11 改动

`plugins/speech/realtime.c/.h` 增加两项可组合操作：

- `agent_realtime_update`：发送更新，不清除或提交输入，期间仍可上传和接收 ASR。
  等到 `session.updated` 才解除更新状态；调用方回调继续校验配置回显。
- `agent_realtime_commit_input`：只提交完整音频，不隐式触发生成。原 `commit`
  接口仍组合提交与生成，保留原调用方行为。

更新待确认时禁止第二次更新、生成、工具结果发送及跨轮清空。写入返回 BUSY
表示零字节已发送，不能据此接纳更新确认；重入、取消、超时、越界和失败不自动
重播。新接口没有增加音频缓冲或网络任务，也没有放宽最终输入和响应身份规则。

50/50 ASan/UBSan 主机测试通过。新增用例覆盖 1/7/113 字节分片、半条 ASR 事件
期间更新、持续上传不丢样、草稿生成期间保留未提交输入、只提交而不生成、重复
提交、无效配置、未发送时的错误确认、配置回调拒绝及取消/超时/网络错误。
另有 3 项 Python 离线检查通过，验证转写预览替换、比较保留否定/小数/内部空格，
以及预检不联网、输出目录不复用。

正常音频和无音频构建通过。正常应用 1540032 B，距原 1540096 B 上限剩 64 B；
没有使用诊断余量。SHA256：
`0df75c463473f342a3fcd7f22a9407e4277dec6d019660b21c7bae83d18acd0c`。
该构建仍是旧的运行路径标识，**未烧录，不是已启用的 0.11.74 固件**。
2MiB 上下文、200KiB 历史预算和 448KiB 录音槽保持不变。

## 接入工作尚未完成

下一步是在原有空闲工作区内接入这个协议，替换容易切碎输入的实验预取路径，
不用两条常驻连接叠加内存。必须同时实现：

1. 临时转写的有限版本和消息编号管理；生成响应绑定到当时提交的候选文本。
2. 完整提交确认与最终转写对应，候选与完整输入不一致就不播；空转写仍不能
   当作静音，未完成改口仍需继续听或追问。
3. 一次有界草稿、超时与取消；纯回答和工具过程话语分别校验，保留现有执行后
   才能宣称成功的规则。未播放草稿不写入设备长期历史。
4. 在原 Flash/RAM 预算内编译，通过主机故障检查后，固定至少三轮连续实机
   对话验证完整输入、普通话/粤语再次唤醒、提示音、回答延迟、DMA 和最低堆。

这些是同一个完整目标的后续工作，不将主机通信可行性当成设备功能完成。

## UX-37：设备路径与固定三轮实验

已新增一个有限草稿控制器：临时转写稳定120ms后最多准备一次，原始录音继续
上传；本地收音正常结束、一次完整提交且最终转写编号匹配提交确认后，才允许
核对草稿。任何文本修订永久作废该草稿，不因后续文字变回去而重新放行。
比较只忽略首尾标点/空白，保留中间空白、小数点和否定词。

完整匹配还不是执行授权：候选必须是完整单条音频消息、在40KiB借用缓存内、
无未执行成功声明；设备/记忆过程语句还经过既有将来式检查。候选无效而完整
输入有效时，同一连接恢复正常工具提示并重新请求回答。协议/输入不完整才
允许在无回答和动作的前提下恢复一次完整录音。没有第二个TLS任务、新PCM堆
分配或上下文降容。实验开关仍默认关闭。

主机新增/更新检查覆盖完整提交的身份、预览编号变化、过期响应、改口再改回、
空转写、上传/本地端点失败、取消、草稿溢出、拒绝函数调用、音频随机分块及
配置更新确认。一次真实问题在烧录前被测试抓住：本地端点失败不能进入恢复。
保留01–04初始失败日志，最终75和76各50/50通过ASan/UBSan检查；正常与关闭
音频两种构建均通过。正常应用1539776B，原1540096B预算余320B；分区未改。

### 后续收敛方向

保留“边听边准备”的产品方向，停止把“前缀稳定120ms”当成足够的意图证据。
下一阶段须先解决候选内容足够完整的判断，以及废弃草稿与正式会话的隔离。
当前结果尚不能确定角色泄漏来自服务端更新语义、之前的草稿会话内容，还是
提示文本本身；不应仅调等待时间就再次烧录长测。官方客户端文档目前列出
response.create/cancel，没有为本模型证实临时独立会话输出或删除任意项的接口；
不可直接套用另一家API的conversation:none或item.delete参数。
参见[当前官方客户端事件](https://help.aliyun.com/zh/model-studio/client-events)。

过程语句“将来式”也不能保证语义符合最终要求。对改口控制，后续应禁止在
完整意图校验前说出具体参数；普通问候不得以“我来”这种空过程词冒充答案。
这些是尚未完成的工作，1秒有效回复与48KiB资源目标继续记为未通过。
