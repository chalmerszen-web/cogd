# UX105：提前备答的接收调度实验与回退

关键词推测和音频预取在前两轮成功：准备语首批 PCM 分别早于最终转写
3995/3693ms 到达。但第三轮提前停止录音，遗漏“不要蓝色，改成绿色”，
随后实际误设蓝色。本轮不能作为速度或可靠性通过；接收调度改动已撤回，
设备恢复 0.11.72-summary 监听。保留的 0.11.138 源码只合并重复编码器，
没有宣称解决响应延迟。该版已编译、未烧录验收；正式安装包没有更新。

## 本轮假设与范围

隔离 ASR 原先每发送一块 464 样本 PCM 后，只做一次最多 512B 的零超时读取。
如果临时转写分片或成批到达，可能跨若干次上传才能处理完。137 实验在
零超时读取中最多连续处理八次，并在调用间检查两毫秒预算；遇到空读即返回，
非零超时仍只读取一次。单次传输或解析不能被该预算强制抢占。

这是调度假设，没有网络包抵达时间能证明它就是延迟主因。UX81 曾在 Omni
音频接收尝试类似策略，未证明收益并已回退；本轮仅针对隔离 ASR 的文本事件。
端点规则沿用136，模型、阈值、输入块、缓冲、任务栈及分区不变。

预先限定一组三轮低音量改口测试；只有完整且健康才增加一组简短问候。
本轮改口失败后没有执行第二组，也没有反复重播挑选通过结果。

## 第三轮遗漏的证据

保留设备录音46720样本，即2920ms。本地 SenseVoice 识别“请把灯调成蓝色。”，
云端也是“把灯调成蓝色。”，没有后半句改口。本地识别不是主观试听，但说明
不能只指责云端把一份完整改口录音识别错了。

录音SHA256：`376593279376b7aee5922558edde2e46083dc003fbb14a24501984dc6325dcf7`。
首次“把灯”临时转写在record_at之后3364ms才到达，采集已经结束；此前只有
空pending、“But”、“马灯”等错误草稿。136保留已有待续说状态的规则没有
及时收到有效提示，因而续听额度为0。常规固件没有逐帧提示发布时间证据，
不能据此唯一归因于接收调度、VAD或网络。

136三轮“绿色”临时转写相对上传结束标记分别为+28/-349/+297ms；137为
-105/-787/缺失。不能笼统地称136的所有临时改口都在上传结束后才到达，
也不能把上传结束时间等同于本地麦克风采集结束时间。

后续诊断应复现这份失败采集的本地逐帧结束判定，先解释为何在有效意图提示
到来前停录，再考虑缩短等待。不能靠更早执行猜测颜色来掩盖输入不完整。
