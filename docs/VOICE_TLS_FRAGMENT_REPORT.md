## 主机验证与构建

UX472 对两个实际域名各进行一次 TLS 1.2 握手，验证证书和主机名，只解析协议报文，无认证 HTTP 请求或私人录音上传。申请 4096 B 时，DeepSeek 回显 max_fragment_length 扩展；DashScope 未回显。扩展语义见 [RFC 6066 第 4 节](https://www.rfc-editor.org/rfc/rfc6066.html#section-4)。这是当时主机握手结果，不是 C3 上的兼容性或性能证明。

本地固定 SDK 的实际输入/输出上限为 16384/2048 B，申请上限取两者较小值。因此 UX473 只对 `api.deepseek.com` 申请 2048 B，未修改 SDK 配置、千问连接、证书验证、模型、阈值、任务栈、上下文或分区。主机唯一一次 2048 B 握手确认客户端与服务端均回显 `03`。专用 C11 策略测试通过 ASan/UBSan，但使用接口桩，未覆盖实际 SDK 的握手片段重组。

仅一次正常应用构建：1534128/1540096 B，剩 5968 B；新增策略无堆分配、任务或 PCM。应用 SHA256：`7fce2ea8b603361dc9407a0a92dc7c82a8f7a9d2920d73ac4f8ce659ce94053f`。全部关键自有 C 编译单元最终采用 C11。保留未执行的初稿命名参数构建脚本、将 OFF 宏误当作必须显式为 0 的冻结校验失败，以及默认 diff 检查的原有 CRLF 警告；它们不是成功验证。

## 实机失败

只执行一组普通话/粤语/普通话三轮，每轮一次唤醒尝试。三轮均命中并取得完整输入；随后均未完成最终业务：一次 Store access fault、一次 Load access fault、一次 TLSF 分配器断言，共三次明确复位。测试程序退出 1，外层恢复程序退出 0，不能把恢复成功记为对话成功。

日志中的异常 PC 分别落在 TLSF 空闲链表操作和 memcpy。原始栈字涉及 HTTP/TLS 连接、证书读取、动态 RX 与 lwIP；栈字地址解析不等于可靠完整调用栈。当前 SDK 的动态 RX 按记录尺寸分配，而握手片段重组在关闭可变缓冲长度时使用静态输入容量检查；该容量关系是需验证的怀疑路径，尚未完成独立复现，不能宣称已证明全部崩溃根因。

复位打断了“完整回复→再次唤醒”的连续过程，也重置堆低水位和协商计数。三次命中不能作为快速重唤醒证明；重启后的 min_heap 不能作为全程内存验收；没有正常完整最终回复，未运行声学速度验收脚本，也不报告这组三轮的一秒达标率。没有补组、放宽门槛或再次烧录抢救这一候选。
