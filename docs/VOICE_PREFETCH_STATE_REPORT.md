## 本次改动

新增默认关闭的 `AGENT_RT_DIAGNOSTICS`。诊断版 0.11.73 只在事件被拒时记录前后
状态、响应编号的 CRC32、输入/响应轮次和 PCM 字节数；不改变协议、工具权限或
最终输入完整性检查，不在新增状态记录中输出语音、密钥或原始响应编号。
正常构建不会包含这段诊断路径。

七份已有主机协议记录共 545 个事件，没有复现设备上的响应编号异常。因此没有
按猜测放宽身份校验。新增主机用例区分正常取消、半个 PCM 样本、错误响应编号及
终止事件元数据；合成用例只证明分支可检测，不等于已证明设备故障原因。

## 实机：只做一组三轮改口

固定输入：“请把灯调成蓝色，不对，不要蓝色，改成绿色。”预取开、连接复用关。
测试前约定只跑三轮，并无条件恢复冻结的 72；没有为得到好结果重复该组。

| 项目 | 结果 |
|---|---|
| 首次唤醒、完整输入、最终任务 | 均 3/3 |
| 硬件动作 | 三轮均只设置绿色；未执行中途的蓝色要求 |
| 整段录音恢复 | 3/3；没有可接受的预取命中证据 |
| DMA 丢失 / 观察到的复位 | 0 / 0 |
| 累计最低空闲堆 | 29,472 B，低于 48 KiB 目标 |
| 外录输入定位 | 三轮均未通过，不报告声学延迟或咻音验收 |

有两次 `response.audio_transcript.delta` 被拒，前一条日志分别为“好的，灯已经”
和“好的，已”。当时响应编号匹配且尚无 PCM。这是拦截提前宣称成功的策略取消，
不能归类为网络故障，也不能靠删除保护来提速。

第三轮另有一次 `conversation.item.input_audio_transcription.completed` 被拒。
日志不足以区分未知输入编号、提交状态、重复内容或转写乱序，故根因仍未确定。
但此前已经收到一个空转写；按现有完整输入规则，这本身就要求恢复整段录音。
即使消除后续协议错误，该轮也不能直接升级为预取命中。

## 同一录音的三个主机对照

导出第三轮已有录音，没有再录新音频。16 kHz 单声道，104,576 样本、6.536 秒；
PCM SHA256 为 `850af350ae9f3bc11eef0e2af53682a027f0b749d61033544c131426b0a35d3e`。
整段在本地 SenseVoice 和设备整段恢复路径中都识别出了完整改口句。
切出的半秒片段缺少上下文，本地识别不作为逐字真值。

固定同一模型、提示词、工具声明、512 样本分块，原探针统一追加两秒静音尾部。
以下每种条件只有一次请求，无重连、重试、播放或工具执行。

| 云端分段设置 / 上传速度 | 分段数 | 空转写数 | 非空转写 |
|---|---:|---:|---|
| 200 ms / 实时 | 6 | 3 | 调成。 / 不要拦。 / 改成。 |
| 800 ms / 实时 | 2 | 0 | 把灯调成蓝色。 / 不要蓝色，改成绿。 |
| 200 ms / 两倍速度 | 6 | 3 | 调成 / 不要拦。 / 改成。 |

三次都上传完整文件，转写均按来源顺序到达。两倍速度不是设备真实包到达时间的
重建；它仅检查这一发送速度差异。800 ms 减少了本片段的碎片和空转写，但仍漏词，
不能据此直接更改设备默认参数。这里没有测量用户说完到扬声器出声的时间。

这组结果说明：在本片段上，过短的分段会使猜测依据不完整，而改变上传速度没有
消除该现象。它不是总体识别率评估，也没有证明所有旧故障具有同一根因。

## 后续实现边界

1. 唤醒后继续并行连接、上传；把临时转写视为可修改的信息。
2. 对稳定意图片段预先生成一个可撤销候选，用输入版本绑定文本及音频。
3. 后续补充、否定或改口使旧候选失效；缺词不能等同于“意图没有改变”。
4. 句末播放结束音效；仅在完整转写与候选一致时接续缓存音频。工具调用仍在最终
   输入确认后执行，过程提示也不得提前宣称已经执行。

下一步先隔离云端分段与完整转写的结合方式，避免一次短停顿就提交残缺语句。
不直接开启当前预取，不把增加静音阈值或清除空转写保护当作已完成的优化。
只有同一输入不再触发整段重传，才值得评价提前准备音频的真实收益。
