# UX171：文字辅助弱语音的固定录音对照

2026-09-29。当前过早结束不能靠“候选音频已下载”证明解决。本轮用八份冻结录音的
实机元数据检查结束策略，**定位到320ms严格续说窗口对两个失败片段的影响**。
宽松对照保留了两个片段的改口尾句；有时限原型仍截断其中一段，因此均未烧录。
整体目标仍未完成，没有新增录音、云请求或连续硬件组。

## 已排除与方法

先检查官方VAD是否修改音频，发现UX169独立实机程序已经逐帧memcmp原始/调用后
缓冲，2503帧未修改；没有重复烧录验证该假设。

实际C3原厂MODE2输出、能量、原ASR通知和源时钟使用UX169固定八份资料。基线为
当前203端点；全部八段的状态、结束、语音量、静音量和累计额度与旧记录一致。
主机重建当前核心，用ASan/UBSan分别执行实际C代码；没有用Python仿写端点。

宽松对照只允许当前meaningful TEXT在原320ms严格续说窗口之外辅助两个当前强帧。
强帧仍要求官方分类及两份能量同时过原阈值，未改变起声、能量、700ms静音或
1000ms累计额度。这是比“仅新文字有效”更宽松的对照，旧文字可能支持噪声，
**不是可部署策略**。冻结后续通知来自原8秒采集，不是假装新采集取得的网络结果。

都是4秒NO_SPEECH。两个短句控制及旧完整改口参考不变。三个完整8秒片段的结果：
第一段多留380ms，后两段由约3.3秒保留到约6.5秒。时长不是声学延迟成绩。

## 保存PCM的本地核对

使用固定本地SenseVoice int8，分别转写完整8秒、基线裁剪和宽松裁剪，没有补造
任何尾音。后两段的基线只识别到“不对”，宽松裁剪识别出之后的改口尾句，文字
与各自完整8秒转写一致。第二段完整录音和宽松裁剪都误识别为“改成黑色”，
不能写成绿色识别通过；第三段均有“请把它”差异。模型判断会出错，不代替真人
听感。第一段基线已经包含完整改口，因此不能把额外380ms全部称作必要改善。

## 有限的新文字原型

进一步只让新增长的有效文字提供320ms辅助：忽略标点重复，文本缩短后重新增长
到旧长度不续期，声段开始/定稿撤销。两项提取边界断言通过。新状态只在产物目录
的独立C原型中存在，未进入生产文件。

事件时间按板上ASR时钟减record_at、向上取整20ms映射，未搜索偏移；这不是实际
消费通知的精确源帧时间，不能据此证明C3调度或延迟。三个结束点为6220、3760、
6480ms；第二段仍只转写到“不对”。未扫描其它时限，也未以宽松版本代替此失败。
这表明短文字计时器不足以复现宽松对照的完整输入，下一步应区分当前活动声段与
滞留文字，而不是把任意TEXT永久作为续说许可。

生产者的独立source_bound目前依据四票能量事件加320ms推导上限。若消费者允许
在该窗口外由两票继续，旧证明失效；必须同步给出新的采样上界证明，不能只改
消费者然后依靠更长录音碰运气。候选音频与动作仍由最终输入确认后放行。
