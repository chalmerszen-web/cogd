# UX89：弱音改口的提前停录与失败录音保留

后续 UX90 已补齐三轮完整设备录音，见本文末尾。延续采集的诊断三轮都完成绿色
任务，但固定 8 秒窗口不是提速方案，已撤下；当前设备仍为 72，预取关闭。

2026-09-27。**三轮弱音输入均被设备提前截断，其中第二轮实际设置了错误的蓝灯。**
失败录音、外部录音和逐帧状态均已保留。两个离线续说候选都会延长部分噪声拖尾，
因此均未采用，也未烧录。设备已恢复 `0.11.72-summary` 的 fast/capture 监听，
连接复用开启、预取关闭、灯关闭。正式安装包不变，一秒有效回复仍未通过。

## 本轮改动

`continuous_rewake.py --retain-failed-capture` 在失败当轮结束后暂停 wake，立即
导出设备录音，再恢复 wake；不重开 voice 或修改模型配置。导出前后核对采集
起止时间、样本数和完成计数，防止把上一轮录音当作本轮。导出限时 30 秒，错误
时保留录音并终止该组。普通测试路径不变；这个诊断不计入速度或快速再唤醒验收。

使用原来冻结的 `0.11.120-protocol-diag`，生产 VAD、滤波和路由未改。只运行一组
三轮，普通话/粤语/普通话唤醒，正文都为普通话。正文播放增益 0.25，比之前 0.35
低约 2.92 dB，唤醒增益不变。这是预先指定的弱音条件，不是 119 失败的严格同条件
重现，也不是新增真人材料。

## 结果与原因范围

完整输入为“请把灯调成蓝色，不对，不要蓝色，改成绿色”。

|---|---:|---:|---|---|
| 1 | 3240 ms | 3272 ms | 请把灯调成蓝色。不对。 | 无 |

| 3 | 3960 ms | 3992 ms | 请把灯调成蓝色。不对。 | 无；灯仍为上一轮的蓝色 |

首次唤醒 3/3；完整输入和最终绿色任务均 0/3，候选采用 0/3。独立本地 ASR 对三份
设备原始 PCM 的识别同样止于蓝色或“不对”，没有绿色后半句。163/145/199 帧的
录音能量与板上元数据完全相同；CRC 和生产 C 端点状态逐帧重放也全部一致。
外部麦克风三轮都录到了绿色后半句，因此证据支持**本地停录提前**，不能只归因于
云端转写漏字。

固定两秒前缀的外录对齐通过；结束咻音约早于完整播放内容结束 2.445/2.800/1.745 秒。
这是诊断用声源对齐和音效定位，不是首音素或回复速度验收，没有主观试听结论。

局部记录里有两三帧满足强人声条件，却未满足四帧续说条件；较弱支持又已超过
320 ms 有效期，静音计时继续累加。这个观察解释了本组三段短音节为何未能续录，
不证明任意两三帧都是人声，也不确定噪声的电气来源。

## 为什么两个候选没有进入固件

只在已有 12 份元数据上运行两个独立 C 原型，没有再增加物理对话或云端重试：

1. 弱支持允许使用纯能量证据，有效期从 320 ms 延长到原结束窗口 700 ms。
2. 保留原判定，在频谱拒绝至少 120 ms 后的一次短音节重新开始时，给予有次数限制
   的续说支持；严格续说才补充额度。

两者都能让这三份弱音前缀越过旧结束点，但也让 UX88 第二、三轮已有的噪声拖尾
越过旧结束点；第二个候选还延长了 62 第一轮。反事实输入只有已保存的前缀，
不能证明缺失后半句会被完整录到。因此两个候选均拒绝，没有把“没那么早停”
当作修复通过。生产端点代码保持与 120 冻结版本相同。

诊断工具另修复了输出完整性问题：一次 WSL 标准输出只收到 28672 字节却返回成功。
C 重放工具增加独占 `--output` 文件，Python 再校验总帧数和每帧源时间，避免尾部
丢失被误报成功。原始截断输出和未成功的 shell 重定向尝试保留，新文件路径的三轮
重放通过；原三轮分析的帧数本身也完整，没有借此改写原失败结果。

## 对提前准备回复的影响

“边听边准备”仍是方向：关键词先准备路由、回复和静默音频缓存，完整输入确认
后再播放。通用的“我来调整灯光”可以跨颜色改口复用；具体颜色和 GPIO 动作必须
取自最终输入。不能靠补一句引导撤回已经播放的错误答案或已执行的动作。

当前实验路径已经具备候选版本、撤销和最终校验，但本轮证明“录音成功结束”
并不等于“用户已经说完整句”。下一步需要解决这个输入边界，不能继续只根据
相同的能量/频谱票数放宽阈值，也不能把提示音或准备语算作一秒有效回答。
