## 原版与现场证据

USB COM5 实际读取为 0.12.4-clock，模型 `xiaoyan_el24_verify48_256ms`、阈值 740、preconnect=capture。先发现设备未联网；按用户提供的新网络完成配网并确认 Wi-Fi 和校时成功。凭据未写入源码或测试报告。

原版第一组自动测试的唤醒尝试数为 1/2/1；同时出现输入缺字和一次空输入超时，整组 FAIL。该组附加状态查询会改变主机送话时序，因此不能把所有输入问题归因于固件。第二组使用原三轮脚本，每轮只允许一次呼叫，完整输入和回答均 PASS；原问题具有间歇性，未将第二组成功称作修复。

临时版本 0.12.5-rewake-diag 只增加被动观测，不改变模型、阈值或唤醒判定。三份模型和原静音初态数据哈希不变；新增固定 8 行原子记录，静态数据约 171 B，不复制 PCM、不分配任务或堆内存，也不在音频任务打印。该版本另有一组三轮完整对话 PASS。

在真实板上固定播放近词“你好小燕”，间隔 50 ms 后播放正确唤醒词，得到以下设备时间线。阈值 740 对应 logit Q8.8 约 268。

| 设备时间 ms | 观测 | 主／辅分数 | 剩余冷却 ms |
|---:|---|---|---:|
| 120851 | 主候选创建 | 668 / -346 | 1500 |
| 121135 | 复核窗口过期，没有最终唤醒 | -2508 / -1141 | 1212 |
| 122154 | 后续正确唤醒主投票满足，仍被冷却阻挡 | 876 / 1046 | 188 |
| 128461 | 冷却后同一正确唤醒音被接受 | 995 / 938 | 1500 |

这确认了“失败候选仍占用长冷却”的实机路径。它可以使用户连续呼叫多次才成功；不把控制输入复现声称为用户所有漏唤醒场景的唯一原因。

## 改动

- 仅最终通过主／辅复核才提交 24000 样本（1.5 秒）冷却，保留通用 `kws_detector.c` 原有行为。
- 每个候选只有一个不可延长的 4096 样本（256 ms）复核窗口。新候选还需要主分数连续 3 块低于阈值（96 ms）；稳定模式为 4 块，防止持续高分反复打开窗口。
- 普通解除监听清理候选、复核和释放状态，但保留已成功事件的冷却；时钟断块重置全部时序状态并重新预热。
- `voice status` 在启用请求已受理、实际监听尚未恢复时报告 `rearming`，真实监听及麦克风就绪后才报告 `listening`。保留原有 500 ms 防回声保护。
- 同步静音初态的类型化导出、源码哈希绑定及模型来源清单。没有重新训练、降低阈值或改变神经网络权重；原有 Python UX277 参考实现明确标为历史版本。
