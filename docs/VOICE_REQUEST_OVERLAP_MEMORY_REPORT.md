# UX151：接话与正式请求同时运行的内存门槛

2026-09-29。完成一组三轮实机诊断，**不恢复完整工作区同时运行的方案**。
有效测量窗口内，只预留正式请求所需的两块内存，实际空闲堆就降到
**41,364 B**，低于原定 48 KiB。没有把接话音效或提示语算作正式回答，
没有完成稳定一秒响应验收。设备已恢复 0.11.72-summary，源码仍为 185。

## 为什么先测内存

当前已经实现部分 ASR 提名、异步候选生成、完整输入核对和候选撤销。
任务提示语获准播放后，185 还能提前建立 DeepSeek 的 HTTPS 连接。
但正式请求正文仍要等待候选下载完成、任务退出后再发送，因此还存在串行等待。

接话阶段的 28,216 B 工作区包含候选任务、协议解析、源帧记录和播放缓冲；
正常 Agent 需要 29,836 B 状态加 24,577 B 请求缓冲。直接保留双方合计
82,629 B，尚未计入 TLS 等分配。上下文单条记录原有容量仍可能需要整个
请求缓冲，不能把它随意改借到较小的尾部；候选任务栈也不能在退出前复用。
此前 69/70 的完整请求并行已有低内存和网络失败记录，本轮没有照搬。

## 唯一实验

189-memory-probe 是临时诊断固件。原有 HTTPS 预连接成功后，如果任务接话
仍在接收，主网络任务各分配一次完整状态和请求缓冲，记录空闲堆及最大块，
随即释放。没有绑定 engine/context 指针，没有发送额外正文或执行额外工具，
没有新任务、缩栈或缩减任何上下文容量。失败或取消也释放已经分配的内存。

固定三轮使用原 UX144/145 的“现在灯是什么颜色？请简单回答。”素材、增益
0.25、普通话/粤语/普通话唤醒、idle/reuse/prefetch 开启。没有补跑失败轮，
也没有进行第二组。三次首次唤醒成功；仅第一轮候选及时到达并进入测量窗口。
另外两轮候选在原有等待期限内未准备好，取消后回退，不能当作两次内存通过。

| 第一轮现场记录 | 字节或时间 |
| --- | ---: |
| 分配前实际空闲堆 | 97,692 B |
| 分配 29,836 B 状态后 | 66,968 B |
| 再分配 24,577 B 请求缓冲后 | **41,364 B** |
| 此时最大连续块 | 21,504 B |
| 释放两块后的实际空闲堆 | 97,692 B |
| 探针耗时 | 1 ms |
| 探针时刻至候选接收完成 | 1,165 ms |

两次分配均成功，采样时候选任务尚未完成。这是同一时刻的实际空闲堆，
不是把多个内存区的历史最低值相加所得。逻辑分配大小与实际堆下降分别保存，
没有未经验证地把差值全部归为分配器开销。连请求正文的序列化、接收解析都
尚未运行，就已经不足 48 KiB，因此直接增加完整工作区不满足必要条件。
本次没有测量真正并行 HTTP 的最终峰值，不能据此推算其速度或稳定性。

三轮最终 ASR 分别为“现在灯是什么颜色？”、“现在灯是什么？”和
“现在灯是什么？”，完整输入 **0/3**，原测试退出码 1 保留。第一轮有一次
灯状态查询，核心任务通过；后两轮缺少“颜色”，核心任务也未通过。对话中
未见 setter、复位、watchdog、panic、DMA 丢失或播放欠载。SDK 历史最低堆
40,588 B、网络任务最小剩余栈 1,968 B 单独记录，不能用恢复后的数值替代。
外部原始录音已保存；本轮没有进行声学起声验收或主观试听，不给出声学延迟。

## 下一步的具体边界

仍可尝试减少同时存活的内存：先仅用请求缓冲序列化并发送首次正文，候选
退出后才分配回复状态。但当前首次正文依赖消息工作区，用户输入的持久化
也不能与上下文 scratch 直接别名。必须先在主机证明新的分阶段序列化与现有
请求逐字节一致、保留全部输入与历史、取消和错误时正确释放，才能再次上板。
这只是下一项实现方向，不是本轮已经完成的优化；本轮不扩大为新的反复调参。
